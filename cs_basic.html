SCENE 2
SSD → RAM으로 프로그램 복사
~50ms
OS가 SSD에 있는 eldenring.exe의 핵심 코드를 RAM으로 복사해.
왜? CPU는 SSD를 직접 읽을 수 없거든. CPU가 읽을 수 있는 곳은 RAM뿐이야.

SSD는 "창고"고, RAM은 "작업 책상"이라고 생각해.
창고에서 필요한 서류를 꺼내서 책상 위에 펼쳐놓는 거야.

SSD = 네 방 책장 (용량 큼, 꺼내는데 시간 걸림)
RAM = 책상 위 (작지만, 손만 뻗으면 바로 잡을 수 있음)
CPU = 너의 뇌 (책상 위에 있는 것만 읽을 수 있음)
↓
SCENE 3
CPU가 첫 번째 명령을 읽기 시작
~100ms
RAM에 코드가 올라왔으니, 이제 CPU가 첫 줄부터 읽기 시작해.

CPU 안에 "Program Counter(PC)"라는 게 있어. 이건 "지금 몇 번째 줄 읽고 있는지"를 가리키는 화살표야.
PC가 "1번 줄 읽어!" → 읽음 → "2번 줄 읽어!" → 읽음 → ... 이걸 초당 수십억 번 반복.
CPU가 명령을 읽는 과정 3단계:
① Fetch = RAM에서 명령을 가져옴 (책상 위 서류를 눈앞으로 당김)
② Decode = "이건 덧셈이다" "이건 메모리 읽기다" 해석
③ Execute = 실제로 실행 (계산하거나, 값을 옮기거나)
↓
SCENE 4
CPU가 일을 나눠줌 (멀티스레드)
~200ms
엘든링은 혼자 일하면 너무 느려. 그래서 여러 스레드(일꾼)를 만들어:

• 메인 스레드: 게임 로직 총괄 (보스 AI, 플레이어 입력 등)
• 렌더 스레드: GPU에게 "이거 그려!" 명령을 보내는 담당
• 로딩 스레드: SSD에서 다음에 필요한 파일을 미리 RAM으로 올리는 담당
• 오디오 스레드: 배경음악, 효과음 재생
• 물리 스레드: 물리 계산 (중력, 충돌)
식당을 오픈한다고 생각해.
셰프(메인 스레드)가 혼자 요리+서빙+계산+청소 다 하면 느리잖아.
그래서 서빙 담당(렌더), 재료 가져오는 사람(로딩), DJ(오디오) 등을 따로 고용하는 거야.
CPU 코어가 여러 개니까 각 코어에 스레드를 배정해서 동시에 일함.

SCENE 6
텍스처/메시를 GPU의 VRAM으로 전송
로딩 중

SCENE 7
SSD가 HDD보다 빠른 이유
HDD: 동그란 디스크를 물리적으로 회전시키고, 바늘(헤드)을 이동시켜서 읽음.
LP 레코드판에서 노래 찾는 것처럼 — 원하는 위치까지 바늘을 옮겨야 해.
→ "찾는 시간" 때문에 느림 (수 ms)

SSD: 물리적 움직임이 없음. 전기 신호로 바로 읽음.
USB 메모리와 같은 원리(플래시 메모리). 주소만 알려주면 즉시 데이터 나옴.
→ 물리적 이동 없이 전기적으로 접근 (수십 μs)
HDD = 도서관에서 책 찾기. 서가까지 걸어가서 뒤져야 함.
SSD = 전자책. "42페이지!"라고 말하면 바로 뜸.

그래서 엘든링을 SSD에 설치하면 로딩이 2~3초인데,
HDD면 20~30초 걸리는 거야.

SCENE 9
스트리밍 방식 — 전부 RAM에 올리지 않음
2분짜리 풀HD 영상을 전부 RAM에 올리면 수 GB → 낭비

그래서 "스트리밍" 방식을 씀:
• SSD에서 2~3초치만 RAM으로 읽어옴
• CPU가 그걸 압축 해제 (디코딩)
• GPU가 화면에 표시
• 그 사이 다음 2~3초치를 또 읽어옴
• 이걸 반복

결론: 컷씬은 RAM에 "전부" 있는 게 아니라, "지금 재생할 부분만" RAM에 있어.
넷플릭스 영상 보는 것과 같은 원리야.
영상 전체를 다운받고 재생하는 게 아니라, 보는 속도에 맞춰 조금씩 받아오잖아?
컷씬도 SSD에서 RAM으로 "조금씩 흘려보내는" 방식이야.

실시간 컷씬 vs 사전 녹화 컷씬

① 사전 녹화 (Pre-rendered):

② 실시간 렌더링 (In-game):
보스 등장 씬 같은 것. 네 캐릭터가 그대로 나오잖아? (커마한 모습 그대로)

다만 카메라 이동, 캐릭터 동작이 미리 정해져 있을 뿐.

SCENE 13
포인터 — "주소를 가리키는 변수"가 실제로 하는 일

SCENE 15
GPU가 실제로 그리는 과정
GPU가 드로우콜 받으면 이렇게 처리해:

① 정점(Vertex) 처리:
3D 모델은 점(정점)들의 집합이야. 삼각형 수만 개로 이루어진 그물망.
각 점의 3D 좌표를 → 2D 화면 좌표로 변환 (카메라 시점 적용)

② 래스터화(Rasterization):
삼각형들이 화면의 어떤 픽셀에 해당하는지 계산

③ 픽셀(Fragment) 처리:
각 픽셀의 색깔을 결정. 텍스처에서 색을 읽고, 빛 계산(그림자, 반사) 적용

④ 화면에 출력:
완성된 픽셀들을 프레임버퍼에 쓰고, 모니터로 전송
GPU = 수천 명의 화가가 동시에 일하는 공장.
"이 삼각형 색칠해" "저 삼각형 색칠해" 를 수천 개 동시에 처리.
CPU는 셰프 1명이 순서대로 일하는 거고,
GPU는 일을 잘게 쪼개서 수천 명이 동시에 하는 거야.

SCENE 17
CPU가 RAM에 접근하는 순간들
"CPU가 언제 RAM에 접근하나?" → 거의 매 순간이야. 대표적인 것들:

• player->hp 읽기 → 포인터 따라가서 RAM에서 값 읽어옴
• boss->position 읽기 → 보스 위치 확인하려고 RAM 접근
• 새 오브젝트 생성 (new Arrow()) → RAM의 Heap에서 공간 할당
• 함수 호출 → 스택(RAM)에 리턴 주소와 지역변수 저장
• 배열 순회 → 배열 데이터가 RAM에 있으니까 접근

근데 매번 RAM까지 가면 느리잖아? → 그래서 캐시가 있는 거야!
최근에 읽은 데이터는 CPU 안의 캐시에 복사돼 있어서, 다음에 또 읽으면 RAM 안 가도 됨.
보스전처럼 빠르게 돌아가는 상황에서는:
• 플레이어 데이터, 보스 데이터를 계속 읽으니까 → 캐시에 들어가 있음 → 빠름
• 갑자기 새로운 적이 스폰되면? → 처음 읽는 데이터 → 캐시에 없음 → RAM까지 감 → 살짝 느림
이게 순간적인 프레임 드랍(렉)의 원인 중 하나야.

Q: new로 만든 메모리는 어디에?
A: RAM. 구체적으로는 RAM 안의 "Heap 영역". GPU VRAM 아님. SSD도 아님.

Q: GPU의 VRAM은 뭐야?
A: 그래픽카드에 물리적으로 붙어있는 별도의 메모리 칩. RAM과 완전 별개.

Q: 로딩이 끝나면 SSD는 안 쓰나?
A: 거의 안 씀. 가끔 새 지역으로 이동하면 추가 로딩(스트리밍)할 때 씀.
엘든링은 오픈월드라 돌아다니면서 계속 조금씩 SSD→RAM 로딩함.

Q: 왜 RAM이 부족하면 게임이 느려져?
A: 필요한 데이터를 RAM에 다 못 올리면, 쓸 때마다 SSD에서 읽어야 함.
SSD는 RAM보다 1000배 느리니까 = 프레임 드랍, 끊김.

5. CPU 캐시가 일하는 법
왜 캐시가 필요한가?

CPU는 엄청 빠른데 RAM은 상대적으로 느려. CPU가 RAM에서 데이터를 기다리는 시간이 너무 아까움.
그래서 자주 쓰는 데이터를 CPU 안에 미리 복사해두는 작은 메모리 = 캐시

CPU가 데이터를 읽을 때의 흐름
CPU가 주소 0x1234의 데이터 요청
↓
L1 캐시 확인
있으면 (Hit) → 즉시 사용 (~1ns)
없으면 (Miss) → 다음 단계
↓
L2 캐시 확인
있으면 → L1에 복사 + 사용 (~4ns)
없으면 → 다음 단계
↓
L3 캐시 확인
있으면 → L2→L1에 복사 + 사용 (~10ns)
없으면 → RAM으로
↓
RAM에서 가져오기
캐시 라인(64B) 단위로 읽어옴 (~100ns)
L3→L2→L1 순서로 채워넣고 사용
🧱 캐시 라인 (Cache Line) — 핵심 개념

캐시는 바이트 하나씩 안 가져와. 64바이트씩 한 덩어리(캐시 라인)로 가져옴.
int arr[100]을 순서대로 접근하면? → arr[0] 가져올 때 arr[1]~arr[15]까지 같이 옴 (int 4바이트 × 16 = 64B)
→ 다음 접근들은 전부 캐시 히트! 이게 공간적 지역성 (Spatial Locality)

⚠️ 게임에서의 캐시 최적화 예시

나쁜 예: 적 100마리를 LinkedList로 관리 → 메모리 여기저기 흩어짐 → 캐시 미스 폭발
좋은 예: 적 100마리를 Array로 연속 배치 → 순회할 때 캐시 라인 단위로 쭉 읽음 → 빠름
이게 바로 데이터 지향 설계 (DOD)와 ECS 패턴의 핵심 이유!

6. Heap과 동적 메모리 할당
💡 핵심 답변: new로 할당한 메모리는 어디에?

new로 만든 메모리 = RAM 안의 Heap 영역에 생김.
GPU의 VRAM이 아님. 하드디스크도 아님. 물리적으로 메인보드에 꽂혀있는 그 RAM 위에 생기는 거야.
정확히는: OS가 가상 메모리 주소를 할당하고, 실제 접근할 때 물리 RAM 페이지를 매핑해줌.

new/delete의 실제 동작
단계무슨 일이 일어나나?
int* p = new int(42);1. 컴파일러가 operator new 호출 코드 생성
2. 내부적으로 malloc(4) 호출 (4바이트 = int 크기)
3. Heap 메모리 관리자(allocator)가 빈 공간 탐색
4. 적절한 빈 블록 찾으면 그 주소를 반환
5. 해당 주소에 42를 기록
6. 포인터 p에 그 주소(예: 0x00A3F010) 저장
delete p;1. 해당 주소의 메모리를 "사용 가능"으로 표시
2. 실제 RAM이 지워지진 않음 (표시만 바뀜)
3. p는 여전히 그 주소를 가리킴 → 댕글링 포인터!
🧩 메모리 파편화 (Fragmentation) — 왜 생기나?

Heap은 자유로운 순서로 할당/해제할 수 있어. 바로 이게 문제.

예시: 100바이트 Heap이 있다고 치자:
1. A 할당 (20B) | B 할당 (30B) | C 할당 (20B) | 빈공간 (30B)
2. B를 해제 → [A 20B] [빈 30B] [C 20B] [빈 30B]
3. 이제 50B를 할당하고 싶은데? → 연속된 50B 공간이 없음!
총 빈 공간은 60B지만, 조각나서 50B를 할당 못함 = 외부 파편화

게임에서 수천 개의 총알, 파티클을 반복 생성/삭제하면 이런 일이 반복됨.
→ 해결책: 메모리 풀 (Object Pool)로 같은 크기의 블록을 미리 잡아두고 재활용

🏗️ 가상 메모리 vs 물리 메모리

가상 메모리: OS가 각 프로세스에 "너만의 4GB 공간이 있어"라고 속여주는 것.
프로그램은 0x00000000 ~ 0xFFFFFFFF 주소를 마음대로 쓴다고 생각함.

물리 메모리: 실제 RAM 칩의 주소.

매핑: OS의 MMU(Memory Management Unit)가 가상주소→물리주소를 변환.
4KB 단위의 페이지로 관리. 자주 쓰는 매핑은 TLB (Translation Lookaside Buffer)에 캐시.

🎮 GPU VRAM과의 관계

GPU의 VRAM은 완전히 별도의 물리 메모리야 (그래픽카드 위에 붙어있음).

일반 코드의 new/malloc → RAM (CPU가 접근하는 메모리)
텍스처/메시 데이터 → CPU에서 먼저 RAM에 로드 → GPU API(DX12/Vulkan)를 통해 VRAM으로 복사

Unreal Engine에서 UTexture2D를 로드하면:
1. SSD → RAM으로 텍스처 파일 읽기
2. 디코딩 (압축 해제)
3. GPU 드라이버를 통해 VRAM으로 업로드
4. 렌더링 시 GPU가 VRAM에서 직접 읽음

레지스터
레지스터 — CPU 안의 초고속 메모장 (가장 빠른 저장소)
레지스터는 CPU 칩 안에 물리적으로 박혀있는 저장 공간이야.
크기는 겨우 64비트(8바이트) × 16개 정도 — 아주 소량이지만 가장 빠름.

주요 레지스터 종류:
이름역할엘든링 비유
PC (Program Counter)"지금 몇 번째 명령 읽고 있나"레시피북의 책갈피 — "지금 3단계야"
IR (Instruction Register)"지금 읽고 있는 명령" 보관지금 눈앞에 펼쳐놓은 레시피 한 줄
ACC (Accumulator)계산 결과 임시 저장셰프가 맛본 후 "간이 좀 싱거워" 기억
SP (Stack Pointer)스택의 꼭대기 위치"접시 쌓인 높이가 여기까지야"
MAR (Memory Address)RAM에서 읽을 주소"냉장고 3번 칸 열어!"
MDR (Memory Data)RAM에서 가져온/보낼 데이터"냉장고에서 꺼낸 계란"
엘든링에서 player->hp -= damage; 할 때:
1. MAR에 "player->hp의 RAM 주소" 넣음
2. RAM에서 hp 값(100)을 가져와서 MDR에 넣음
3. ACC에 100 넣고, damage(30) 빼서 ACC = 70
4. 결과 70을 다시 RAM에 기록

이 모든 게 레지스터 안에서 왔다갔다하면서 처리됨.
↓
ALU
ALU — "실제 계산하는 부품"
ALU가 할 수 있는 연산은 단순해:

산술 연산: 덧셈, 뺄셈, 곱셈, 나눗셈
논리 연산: AND, OR, NOT, XOR (비트 플래그에 쓰이는 그것!)
비교 연산: 같은지, 큰지, 작은지
시프트 연산: 비트를 왼쪽/오른쪽으로 밀기

모든 복잡한 프로그램도 결국 이 단순 연산들의 조합이야.
player->hp -= damage * (1 - defense/100);
→ 곱셈 → 나눗셈 → 뺄셈 → 뺄셈 → 이렇게 분해됨.
CU(제어장치)는 "뭘 할지" 해석하고,
ALU(연산장치)는 "실제로 그걸 함".

CU = 감독 ("다음은 덧셈이다! 레지스터 A와 B를 더해!")
ALU = 선수 ("네! A+B 계산! 결과 여기요!")

① Fetch (가져오기):
• PC(프로그램 카운터)가 "다음 명령은 주소 0x0040에 있어"라고 알려줌
• CPU가 그 주소를 MAR에 넣고 → RAM(또는 캐시)에서 명령어를 가져옴
• 가져온 명령어를 IR(Instruction Register)에 저장
• PC를 다음 명령으로 이동 (PC += 4, 보통 4바이트씩)

② Decode (해석):
• CU가 IR에 있는 명령어를 읽음: ADD R1, R2
• "아 이건 덧셈이구나. R1과 R2를 ALU에 보내야겠다"
• 필요한 레지스터에서 값을 꺼내 ALU 입력으로 준비

③ Execute (실행):
• ALU가 실제로 R1 + R2 계산
• 결과가 ALU 출력에 나옴

④ Store (저장):
• 결과를 R1에 다시 저장 (또는 RAM에 기록)
엘든링에서 boss->hp -= playerDamage; 한 줄이 CPU에서 처리될 때:

① Fetch: "다음 명령은 0x0040에 있어" → RAM에서 SUB 명령 가져옴
② Decode: "이건 빼기다. boss->hp 주소에서 값 읽고, playerDamage를 빼야겠다"
③ Execute: ALU가 100 - 30 = 70 계산
④ Store: 70을 boss->hp가 있는 RAM 주소에 기록

이걸 CPU가 1초에 수십억 번 반복하는 거야.
⚡ 3. 파이프라인 — 세탁기처럼 겹쳐서 처리

개념
파이프라인 없이 vs 있을 때
파이프라인 없이 (순차 처리):
명령1: Fetch→Decode→Execute→Store (끝) → 명령2 시작 → ...
4클럭에 명령 1개. 명령 4개 처리하려면 16클럭.

파이프라인 있으면 (겹쳐서):
세탁기 비유를 생각해봐. 빨래 4묶음 해야 하는데:
파이프라인: 각 클럭마다 각 단계가 다른 명령을 처리 중
클럭FetchDecodeExecuteStore
1명령1---
2명령2명령1--
3명령3명령2명령1-
4명령4명령3명령2명령1✓
5명령5명령4명령3명령2✓
→ 4클럭 째부터 매 클럭마다 1개씩 명령 완료! (4배 빨라짐)

빨래 4묶음을 해야 해. 각 빨래는: 세탁(30분) → 건조(30분) → 다림질(30분) → 정리(30분).

❌ 순차: 1묶음 전부 끝내고 → 2묶음 시작 → ... = 8시간
✅ 파이프라인: 1묶음 세탁 끝나면 건조기 넣고, 세탁기엔 2묶음 넣어!
→ 각 기계가 항상 바쁨 → 4묶음이 5시간 30분에 끝남 (30% 절약 아니고 거의 4배 처리량)

문제
파이프라인의 적 — 분기(Branch)와 스톨(Stall)
파이프라인이 항상 좋은 건 아냐. if문을 만나면 문제가 생겨:

if (boss->hp <= 0) { PlayDeathAnimation(); }

CPU가 이 if문을 Decode하는 시점에, 이미 다음 명령들을 Fetch해놨어 (파이프라인이니까).
근데 if의 결과가 TRUE면? → 방금 Fetch한 명령들 다 쓸모없어짐 → 전부 버림 (Pipeline Flush)

이걸 줄이려고 CPU가 하는 것: 분기 예측 (Branch Prediction)
→ "이 if문은 보통 FALSE일 확률이 높으니까, 일단 FALSE 쪽을 미리 실행해두자"
→ 맞으면 그대로 진행, 틀리면 다 버리고 다시 시작 (비용 큼)
엘든링에서 보스 hp 체크를 매 프레임 하잖아?
보스가 아직 살아있는 동안에는 if(hp<=0)이 항상 FALSE야.
CPU가 "어 이번에도 안 죽었겠지?" 예측하고 미리 다음 코드 진행.
→ 99% 맞음 → 파이프라인 계속 잘 돌아감.
→ 보스 죽는 순간 1번 예측 실패 → 파이프라인 한 번 비움 → 미미한 비용.
게임에서의 실제 영향:
매 프레임 수백만 번 분기 예측을 하는데, 예측 실패율이 높은 코드를 짜면 느려져.
→ 적의 상태를 난수로 매번 바꾸는 AI? → 예측 어려움 → 파이프라인 자주 비워짐
→ 이래서 "분기 없이 코드를 짜라"(Branchless Programming)는 최적화 기법이 존재함.

왜 필요?
포인터가 왜 필요한 건데?
이유 1: 큰 데이터를 복사 안 하려고

보스 데이터가 1MB라고 쳐. 보스 AI 함수에 보스 정보를 넘길 때:
• 포인터 없이: 1MB를 통째로 복사해서 넘김 → 느리고 메모리 낭비
• 포인터로: "보스가 여기 있어" 주소 8바이트만 넘김 → 빠름

이유 2: 여러 곳에서 같은 데이터를 공유하려고

"마르기트" 보스가 있는데, AI 시스템도, 렌더링 시스템도, 사운드 시스템도
다 같은 마르기트의 데이터를 접근해야 해.
포인터로 주소만 전달하면 → 모두가 같은 마르기트를 바라봄.
AI가 boss->state = ANGRY; 하면, 렌더링도 같은 boss를 읽으니까 알아서 분노 모션 재생.

이유 3: 크기를 미리 모르는 데이터 (Heap 할당)

적이 몇 마리 나올지 모르잖아. 10마리? 100마리?
new Enemy()로 필요할 때마다 Heap에 만들고, 그 주소를 포인터로 관리.

위험
포인터의 위험성 — 댕글링 포인터 & 널 포인터
댕글링 포인터 (Dangling Pointer):
보스를 죽여서 delete boss; 했어. 보스의 메모리가 해제됨.
근데 AI 시스템이 아직 boss->state를 읽으려고 해!
→ 이미 해제된 주소에 접근 → 크래시(게임 튕김) 또는 이상한 값을 읽음.

널 포인터 (Null Pointer):
Boss* boss = nullptr; → "아직 보스가 없다"는 뜻.
근데 이 상태에서 boss->hp를 읽으면?
→ 주소 0으로 가려는데 거기엔 아무것도 없음 → 크래시
• 댕글링 = 친구가 이사 갔는데, 옛날 주소로 찾아간 것. 엉뚱한 사람이 사는 집 문을 두드리게 됨.
• 널 = 주소를 아예 안 적어놓고 "찾아가!" 한 것. 빈 종이 들고 헤맴 → 에러.

게임 크래시의 엄청 많은 원인이 이 두 가지야.
🏗️ 3. Stack vs Heap — 두 가지 메모리 할당 방식
둘 다 RAM에 있지만, 사용 방식이 완전히 다름
Stack
Stack = 접시 쌓기
함수를 호출하면, 그 함수에 필요한 변수들이 스택에 쌓임.
함수가 끝나면 자동으로 빠짐. 네가 신경 안 써도 됨.

void attack() {
int damage = 50; ← 스택에 쌓임
int finalDmg = damage * 1.5; ← 또 쌓임
} ← 함수 끝 → damage, finalDmg 자동 삭제

스택은 "위에 하나 쌓고, 위에서부터 빼는" 구조. (LIFO: Last In, First Out)
접시 쌓는 거랑 같아 — 마지막에 올린 접시를 먼저 빼야 해.
전투 중에 attack() 함수가 호출되면:
- damage, finalDmg 같은 임시 계산값이 스택에 잠깐 생겼다가
- 공격 처리 끝나면 자동으로 사라짐
- 매 프레임 이런 함수가 수백 번 호출되고 끝나고를 반복

스택이 빠른 이유: 항상 같은 위치(꼭대기)에서만 넣고 빼니까,
CPU가 "어 이 영역 또 쓰는구나" → 이미 캐시에 있음 → 빠름!
↓
Heap
Heap = 빈 땅에 건물 짓기
new를 쓰면 Heap에 메모리가 할당됨. 네가 직접 delete하기 전까지 안 사라져.

Enemy* goblin = new Enemy();
→ Heap에서 빈 공간을 찾아서 Enemy 크기만큼 확보
→ 그 주소를 goblin 포인터에 저장

이 고블린은 함수가 끝나도 안 사라져. 다른 함수에서도 접근 가능.
네가 delete goblin; 해야만 사라짐.
왜 Heap을 쓰냐?

적을 스택에 만들면? → 함수 끝나면 적이 사라짐. 말이 안 되잖아.
적은 필드에 계속 존재해야 하니까 → Heap에 만들어서 오래 유지.

엘든링의 월드에 있는 모든 적, NPC, 아이템 → 전부 Heap에 new로 만들어진 것들.
네가 그 지역을 떠나거나, 적이 죽으면 → delete로 해제.

스택이 "접시 쌓기"면, 큐는 "줄 서기".
먼저 온 사람이 먼저 나감. (FIFO: First In, First Out)

엘든링에서 큐가 쓰이는 곳 — 입력 버퍼:

보스전에서 R1 → R1 → L1 빠르게 눌렀을 때,
게임이 첫 번째 공격 모션 중이라 바로 처리 못해.
→ 눌린 순서대로 큐에 저장: [R1, R1, L1]
→ 첫 공격 끝 → 큐에서 다음 입력(R1) 꺼내서 처리 → 또 꺼내서...
→ 입력한 순서가 보존됨!
스택 = 마지막에 넣은 거 먼저 꺼냄 (접시)
큐 = 먼저 넣은 거 먼저 꺼냄 (줄 서기)

둘 다 "데이터를 순서대로 관리"하는 건데, 꺼내는 순서가 다름.

• 꼭대기 확인: O(1) — 최우선 항목 즉시 확인
• 꺼내기: O(log n) — 꺼내고 나서 재정렬

✅ 상태 확인 (AND 연산 &):

if (status & 빙결) → "빙결 비트가 1이야?" → NO

✅ 상태 끄기 (AND + NOT):
status &= ~독; → "독 비트만 0으로!" → 0000 0010 (출혈만 남음)
보스가 "독 무효" 특성을 가지고 있다면?
if (bossResist & 독) → "이 보스 독 저항 있어?" 한 번에 체크.

🖥️ 1. 운영체제가 뭔데?
"프로그램들의 사장" — 하드웨어와 소프트웨어 사이의 중간 관리자
역할
OS = 건물 관리인
하드웨어(CPU, RAM, SSD, GPU)는 그 자체로는 아무것도 못해. 누가 조율해줘야 해.
OS(Windows, macOS, Linux)가 하는 일:

• 프로그램 관리: 어떤 프로그램이 CPU를 쓸지 결정 (스케줄링)
• 메모리 관리: 프로그램마다 RAM 공간 분배, 서로 침범 못하게 보호
• 파일 관리: SSD의 파일 읽기/쓰기 중재
• 입출력 관리: 키보드, 마우스, 모니터 등 장치와 프로그램 연결
• 보호: 프로그램 A가 프로그램 B의 메모리를 건드리지 못하게 차단
OS = 대형 빌딩의 관리인

• 엘든링 = 5층 세입자 (큰 사무실, 직원 많음)
• 디스코드 = 3층 세입자 (작은 사무실)
• 크롬 = 4층 세입자

관리인(OS)이 하는 일:
- "5층은 회의실(CPU) 13시~13시30분에 쓸 수 있어" (스케줄링)
- "5층 사람이 3층 서류함 열면 안 돼!" (메모리 보호)
- "택배(입력) 왔으면 해당 층에 배달해줄게" (인터럽트 전달)
📦 2. 프로세스 — "실행 중인 프로그램"
exe를 더블클릭하면 "프로세스"가 탄생함
개념
프로그램 vs 프로세스
프로그램 = SSD에 저장된 파일 (eldenring.exe). 아직 아무것도 안 하는 상태.
프로세스 = 그 프로그램이 RAM에 올라와서 실행 중인 상태.

exe 파일을 더블클릭하면 → OS가 프로세스를 만들어줌:
프로세스가 받는 것내용
독립된 메모리 공간코드, 데이터, 힙, 스택 영역 (다른 프로세스 침범 불가)
PCB (Process Control Block)OS가 관리하는 프로세스 신분증 (PID, 상태, 레지스터 값 등)
최소 1개 스레드메인 스레드 (실제 코드 실행하는 일꾼)
프로그램 = 회사 설계도 (종이에 적힌 것, 아직 회사 안 열었음)
프로세스 = 실제로 오픈한 회사 (사무실 임대, 직원 출근, 일 시작)

작업관리자(Ctrl+Shift+Esc) 열면 보이는 목록 = 현재 돌아가고 있는 프로세스들.
엘든링 실행하면 "eldenring.exe" 프로세스가 하나 생겨.
↓
격리
프로세스 간 격리 — 서로 못 건드림
엘든링 프로세스와 디스코드 프로세스는 완전히 분리된 메모리 공간을 씀.
엘든링이 디스코드의 메모리를 읽거나 쓸 수 없어. OS가 막아줌.

왜? → 보안 + 안정성. 엘든링이 크래시 나도 디스코드는 멀쩡.

근데 프로세스끼리 소통하고 싶으면?
→ OS를 통해서만 가능: 파이프, 소켓, 공유 메모리 등 (IPC: Inter-Process Communication)
게임이 크래시 나면?
해당 프로세스만 죽음. OS는 멀쩡. 디스코드도 멀쩡. 바탕화면도 멀쩡.
OS가 "5층 세입자 사망" 처리하고, 다른 층에 영향 안 줌.

블루스크린 = OS 자체가 죽은 것. 그래야 비로소 전체가 멈춤.

• 렌더 스레드: "GPU에 명령 보내는 중..." (코어2)
• 물리 스레드: "충돌 계산 중..." (코어3)

컨텍스트 스위칭
컨텍스트 스위칭 — "일꾼 교대"
CPU 코어 1개는 한 순간에 스레드 1개만 실행할 수 있어.
근데 스레드가 코어보다 많으면? → OS가 빠르게 교대시킴.

교대 과정 (Context Switch):
① 현재 스레드의 레지스터 값 전부 RAM에 저장 ("지금까지 하던 일 메모")
② 다음 스레드의 레지스터 값을 RAM에서 복구 ("이전에 멈춘 지점부터 재개")
③ CPU가 새 스레드의 코드 실행

이걸 초당 수천 번 하니까, 우리 눈에는 "동시에 돌아가는 것처럼" 보여.
컨텍스트 스위칭은 공짜가 아님. 레지스터 저장/복구에 시간이 걸려.
스레드가 너무 많으면? → 실제 일하는 시간보다 교대하는 시간이 더 큼 → 오히려 느려짐.
그래서 게임은 보통 CPU 코어 수에 맞춰 스레드 수를 조절함.
🔒 4. 동기화 & 데드락 — 멀티스레드의 함정
여러 스레드가 같은 데이터를 동시에 건드리면 생기는 문제
문제
레이스 컨디션 — "두 명이 동시에 같은 값 수정"
메인 스레드: boss->hp -= 30; (플레이어 공격)
물리 스레드: boss->hp -= 10; (독 데미지)

동시에 실행되면?
① 메인: hp(100) 읽음 → 100-30=70 계산
② 물리: hp(100) 읽음 → 100-10=90 계산 (아직 메인이 안 썼으니까 100을 읽음!)
③ 메인: hp에 70 저장
④ 물리: hp에 90 저장 (70을 덮어씀!)

결과: hp = 90. 플레이어 공격 30이 사라짐! (원래는 60이어야 함)
이걸 레이스 컨디션(Race Condition)이라 해.
이런 버그는 "가끔" 발생해서 재현이 어려움. 타이밍에 따라 됐다 안 됐다.
가장 찾기 어려운 버그 유형 중 하나. 멀티스레드 게임에서 체력이 가끔 이상하게 되는 이유.
↓
해결
Mutex (뮤텍스) — "한 명만 들어갈 수 있는 화장실"
Mutex = 잠금장치. "이 데이터를 쓰는 동안 다른 스레드 접근 금지."

① 메인 스레드: mutex.lock(); → "내가 쓰는 중! 아무도 오지 마!"
② 메인 스레드: boss->hp -= 30; → 안전하게 수정
③ 메인 스레드: mutex.unlock(); → "다 썼어! 이제 들어와도 돼"
④ 물리 스레드: mutex.lock(); → 이제 내 차례, hp(70) 읽고 → 70-10=60 저장

결과: hp = 60. 정확!
화장실 비유:
화장실(boss->hp) 문에 잠금장치(Mutex)가 있어.
한 사람이 들어가면 잠금 → 다른 사람은 밖에서 대기 → 나오면 열림 → 다음 사람 입장.

다른 동기화 도구:
• Semaphore: 동시에 N명까지 입장 가능 (화장실 칸이 3개)
• SpinLock: 잠겨있으면 "열렸나? 열렸나? 열렸나?" 계속 확인 (짧은 대기용)
• Atomic: 읽기+수정+쓰기를 한 번에 끝내는 특수 명령 (가장 빠름)
↓
데드락
데드락 — "서로 기다리면서 영원히 멈춤"
스레드 A: Mutex1 잠그고 → Mutex2도 필요해서 기다림
스레드 B: Mutex2 잠그고 → Mutex1도 필요해서 기다림

→ A는 B가 Mutex2 풀기를 기다리고
→ B는 A가 Mutex1 풀기를 기다리고
→ 둘 다 영원히 대기 = 게임 프리즈!
좁은 다리에서 두 사람이 마주봄:
"너 먼저 비켜" "아니 너 먼저 비켜" → 둘 다 안 비킴 → 영원히 막힘.

해결법:
• 항상 같은 순서로 잠그기 (전부 Mutex1 먼저 → Mutex2 순서로)
• 타임아웃 걸기 (5ms 기다려도 안 열리면 포기하고 다시 시도)
• 가능하면 Mutex 수를 줄이기

페이징
페이징 — 4KB 단위로 관리
OS는 메모리를 4KB짜리 작은 블록(페이지)으로 나눠서 관리해.

• 가상 메모리의 한 페이지 = 4KB
• 물리 RAM의 한 프레임 = 4KB
• OS가 "이 가상 페이지 → 이 물리 프레임" 매핑표(페이지 테이블)를 유지

Page Fault:
프로그램이 어떤 가상 주소를 접근했는데, 그 페이지가 아직 RAM에 없으면?
→ CPU가 "이거 없는데?" 에러(Page Fault) 발생
→ OS가 SSD에서 해당 데이터를 RAM으로 급히 로드
→ 매핑표 업데이트 → 프로그램 재개
엘든링 오픈월드에서 말 타고 달리는데, 새 지역이 로딩됨:
CPU가 "새 지역 적 데이터 읽어야지" → 그 가상 주소 접근 → Page Fault!
→ OS가 SSD에서 해당 데이터를 RAM에 급히 올림
→ 이 순간이 "미세 끊김"의 정체.

RAM이 부족하면?
오래 안 쓴 페이지를 RAM에서 SSD로 내쫓음(Page Out / 스왑).
다시 필요하면 SSD에서 다시 읽어옴 → 느림 → 렉!
이래서 RAM이 큰 게 중요한 거야.

전부 CPU가 필요해. 근데 코어는 8개.

OS의 스케줄러가 결정:
"이번 5ms는 엘든링 차례, 그 다음 1ms는 디스코드, 그 다음 0.5ms는 Windows 업데이트..."

주요 스케줄링 방식:
방식규칙장단점
Round Robin시간 쪼개서 돌아가며 실행공평함. 게임에 최적은 아님.
Priority우선순위 높은 것 먼저게임에 높은 우선순위 → CPU 많이 받음
선점형 (Preemptive)시간 끝나면 강제로 뺏음현대 OS 기본. 하나가 CPU 독점 못함.
엘든링의 "게임 모드" (Windows):
Windows에서 게임 실행하면 "이 프로세스에 더 높은 우선순위 줘"라고 설정됨.
→ 스케줄러가 엘든링에 CPU 시간을 더 많이 배정 → 배경의 Windows Update보다 우선
→ 이래서 "게임 모드 ON"하면 fps가 안정되는 것.

🎭 2. 가상함수 & 다형성 — "같은 명령, 다른 행동"
면접에서 가장 많이 물어보는 C++ 개념. 반드시 이해해야 함.
문제
문제: "적마다 공격 방식이 다른데?"
고블린은 돌을 던지고, 기사는 칼을 휘두르고, 드래곤은 불을 뿜어.
근데 게임 시스템 입장에서는 그냥 "적이 공격한다" 하나로 처리하고 싶어.

문제: 적 50종류마다 if문으로 분기?
// ❌ 최악의 방법 if (enemy->type == "Goblin") enemy->ThrowRock(); else if (enemy->type == "Knight") enemy->SwingSword(); else if (enemy->type == "Dragon") enemy->BreathFire(); // ... 50개? 새 적 추가할 때마다 여기 수정? 미친 짓
↓
해결
해결: virtual (가상함수) + override
부모에서 virtual로 함수를 선언하면:
"자식아, 이 함수는 네가 네 방식대로 다시 구현해도 돼"라는 뜻.
class Enemy { public: virtual void Attack() { /* 기본: 아무것도 안 함 */ } }; class Goblin : public Enemy { public: void Attack() override { /* 돌 던지기! */ } }; class Dragon : public Enemy { public: void Attack() override { /* 불 뿜기! */ } }; // 사용할 때: 타입 몰라도 됨! Enemy* enemy = GetNearestEnemy(); // 뭔지 모름 enemy->Attack(); // 고블린이면 돌 던지고, 드래곤이면 불 뿜음
다형성(Polymorphism) = "같은 명령, 다른 행동"

모든 적에게 "공격해!" 라고만 말하면, 각자 알아서 자기 방식으로 공격.
고블린은 돌, 드래곤은 불, 기사는 칼. 호출하는 쪽은 누군지 신경 안 써도 됨.

새 적 추가? 그냥 Attack()을 override하는 새 클래스 만들면 끝.
기존 코드 수정 0. if문 추가 0. 이게 다형성의 힘.
↓

👆 3. 참조(Reference) vs 포인터(Pointer)
"둘 다 주소를 다루는 건데 뭐가 다른 거야?"
비교
핵심 차이 한눈에
포인터 (int*)참조 (int&)
정체주소를 담는 변수기존 변수의 별명(alias)
null 가능?✅ nullptr 가능❌ 항상 뭔가를 가리켜야 함
재할당✅ 다른 대상으로 바꿀 수 있음❌ 한 번 정하면 못 바꿈
문법*ptr로 접근, ptr->그냥 변수처럼 사용
안전성위험 (null, 댕글링)상대적으로 안전
int hp = 100; // 포인터: hp의 "주소"를 저장 int* ptr = &hp; // ptr에는 hp의 주소가 들어있음 *ptr = 80; // "그 주소로 가서" 값을 바꿈 → hp가 80이 됨 ptr = nullptr; // 아무것도 안 가리키게 할 수 있음 // 참조: hp의 "별명" int& ref = hp; // ref = hp의 또 다른 이름 ref = 80; // hp가 80이 됨 (그냥 변수처럼 사용) // ref = nullptr; ← 불가능! 참조는 항상 뭔가를 가리킴
포인터 = 주소가 적힌 쪽지. 쪽지를 버릴 수도(nullptr), 다른 주소로 바꿀 수도 있음.
참조 = 별명/닉네임. "마르기트"라는 보스의 별명이 "전율의 마르기트"인 것처럼,
ref는 hp의 다른 이름일 뿐. 항상 같은 대상을 가리킴. 없앨 수 없음.
↓
언제 뭘 써?
실무 규칙
참조를 쓸 때:
• 함수에 큰 객체를 넘길 때 (복사 방지): void Heal(Player& player)
• "반드시 존재하는" 것을 전달할 때
• 읽기만 할 때: const Player& player (복사 없이, 수정도 못하게)

포인터를 쓸 때:
• "없을 수도 있는" 것: Enemy* target = FindEnemy(); → 못 찾으면 nullptr
• 동적 할당(new): Enemy* boss = new Dragon();
• 대상을 바꿀 필요 있을 때: 타겟 변경 등

원칙: "가능하면 참조, 필요할 때만 포인터"
엘든링에서:
• void ApplyBuff(Player& player) — 플레이어는 반드시 존재. 참조.
• Enemy* lockedTarget = nullptr; — 락온 대상, 없을 수도 있음. 포인터.
🛡️ 4. 스마트 포인터 — "자동으로 delete 해주는 포인터"
메모리 누수와 댕글링 포인터를 막는 현대 C++의 핵심
문제
생 포인터(raw pointer)의 문제
Enemy* boss = new Dragon(); // ... 게임 로직 ... if (someCondition) return; // ← 여기서 빠져나가면? delete boss; // ← 이 줄이 실행 안 됨 = 메모리 누수!
스마트 포인터 = 자기가 파괴될 때 자동으로 delete 해주는 포인터 래퍼.
↓
종류
3가지 스마트 포인터
종류규칙엘든링 비유
unique_ptr소유자 1명. 복사 불가. 이동만 가능.유니크 무기 — 한 명만 가질 수 있음. 넘기면 원래 사람은 잃음.
shared_ptr여러 명이 공유. 마지막 사람이 놓으면 삭제.공용 NPC — 여러 시스템이 참조. 아무도 안 쓰면 사라짐.
weak_ptrshared_ptr를 "지켜보기만". 수명 연장 안 함."저 보스 아직 살아있나?" 확인만. 내가 잡아두진 않음.
// unique_ptr: 이 보스는 "이 방"만 소유 std::unique_ptr<Enemy> boss = std::make_unique<Dragon>(); boss->Attack(); // 일반 포인터처럼 사용 // 함수 끝나면 자동으로 delete됨! 누수 불가능! // shared_ptr: 여러 시스템이 같은 적을 참조 std::shared_ptr<Enemy> target = std::make_shared<Goblin>(); std::shared_ptr<Enemy> aiTarget = target; // 참조 카운트 2 // 둘 다 소멸되면 자동 delete // weak_ptr: "아직 살아있나?" 확인용 std::weak_ptr<Enemy> observer = target; if (auto locked = observer.lock()) { // 아직 살아있으면 사용 locked->TakeDamage(10); }
순환 참조 문제 (shared_ptr의 함정):

보스 A가 부하 B를 shared_ptr로 가리키고,
부하 B가 보스 A를 shared_ptr로 가리키면?
→ 서로의 참조 카운트가 1씩 유지 → 둘 다 영원히 안 죽음 = 메모리 누수!

해결: 한쪽을 weak_ptr로. "나는 보기만 해. 잡아두지 않아."
→ 상대가 죽으면 카운트에 영향 없이 자연스럽게 삭제됨.
면접 킬러 질문: "shared_ptr의 순환 참조 문제와 해결법?"
답: "A→B, B→A를 둘 다 shared_ptr로 하면 참조 카운트가 0이 안 돼서 누수 발생. 한쪽을 weak_ptr로 바꾸면 해결."
이 한 줄이면 합격 점수.

질문핵심 답변
"가상함수가 뭐예요?"부모 포인터로 자식의 함수를 호출할 수 있게 하는 것. 내부적으로 vtable에서 실제 함수 주소를 찾아 호출. 다형성의 핵심.
"가상함수의 비용은?"vptr 8바이트 추가, vtable 간접 참조(캐시 미스 가능), 인라이닝 불가, 분기 예측 어려움.
"virtual 소멸자는 왜 필요?"부모 포인터로 자식을 delete할 때, virtual 없으면 자식 소멸자가 안 불림 → 자식 리소스 누수.
"unique_ptr vs shared_ptr?"unique: 소유자 1명, 복사 불가, 가벼움. shared: 여러 곳에서 공유, 참조 카운트로 관리, 약간 무거움.
"순환 참조와 해결법?"두 shared_ptr가 서로 가리키면 카운트 0 불가 → 누수. 한쪽을 weak_ptr로 끊으면 해결.
"참조와 포인터 차이?"참조: null 불가, 재할당 불가, 반드시 초기화. 포인터: null 가능, 재할당 가능. 기본 원칙: 참조 우선, 필요시 포인터.
"상속의 단점은?"깊은 계층은 결합도 높아짐. 부모 변경이 모든 자식에 영향. 다이아몬드 문제. → 대안: 컴포지션(ECS)

🛡️ 4. RAII — "생성할 때 얻고, 소멸할 때 정리"
C++에서 메모리 누수를 원천 차단하는 설계 철학
문제
수동 관리의 문제 — delete를 까먹으면?
❌ 수동 관리:

어떤 함수에서 new로 메모리를 잡았어.
근데 함수 중간에 if (...) return;으로 빠져나가면?
→ 아래에 있던 delete가 실행 안 됨 → 메모리 누수!

게임을 3시간 하면 이런 누수가 쌓여서 → RAM 가득 참 → 느려짐 → 결국 크래시.
❌ 수동 관리 — 누수 발생
void ProcessAttack() {
  int* dmgCalc = new int[1000]; ← 할당
  if (miss) return; ← 여기서 나가면?
  // ... 계산 ...
  delete[] dmgCalc; ← 실행 안 됨! 누수!
}
↓
해결
RAII — "스코프가 곧 수명"
RAII 원칙:
• 생성자에서 자원(메모리, 파일, 락 등)을 얻음
• 소멸자에서 자원을 해제함
• 객체가 스코프를 벗어나면 → 자동으로 소멸자 호출 → 자동 정리!

어떤 경로로 나가든(return, 예외, break) 무조건 정리됨. 누수 불가능.
✅ RAII — 자동 정리
void ProcessAttack() {
  std::vector<int> dmgCalc(1000); ← 생성 = 할당
  if (miss) return; ← 여기서 나가도 OK!
  // ... 계산 ...
} ← 어떻게 나가든 vector 소멸자 호출 → 자동 해제!
수동 관리 = 호텔에서 체크아웃할 때 직접 방 청소하고 나가기
→ 급하게 나가면 청소 안 한 채로 나감 (누수)

RAII = 호텔이 체크아웃 감지하면 자동으로 청소팀 보내기
→ 내가 어떻게 나가든 방은 무조건 청소됨

C++에서 {} 스코프를 벗어나는 순간 = "체크아웃"
소멸자 = "자동 청소팀"
↓

→ vector가 RAII를 내장하고 있어서, 어떤 상황에서든 자동 해제됨.
→ new[]를 직접 쓰면 delete[] 까먹을 위험이 항상 있음.

현대 C++ 원칙: "raw new/delete를 직접 쓰지 마라. RAII 래퍼를 써라."

질문답변
"얕은 복사의 문제점?"포인터 값만 복사해서 두 객체가 같은 Heap을 가리킴. 한 쪽 삭제 시 다른 쪽이 댕글링 → Double Free 크래시.
"깊은 복사란?"새 메모리를 할당하고 내용물을 값 단위로 복제. 독립된 복사본 생성. 안전하지만 큰 데이터에서 느릴 수 있음.
"이동 시맨틱스가 뭐예요?"데이터를 복제하지 않고, 포인터 소유권만 이전. 원본은 빈 상태가 됨. 복사 O(n) vs 이동 O(1).
"std::move는 뭘 하나요?"실제로 이동하진 않음. "이 객체를 rvalue로 캐스팅"해서 이동 생성자/대입연산자가 호출되게 하는 것.
"RAII가 뭐예요?"생성자에서 자원 획득, 소멸자에서 자원 해제. 스코프 기반 자동 정리로 누수를 원천 차단하는 C++ 패턴.
"왜 raw new 대신 vector/unique_ptr?"RAII 패턴이 내장돼있어서, 예외나 early return이 있어도 자원이 무조건 해제됨. raw new는 delete 누락 위험.
이 세 개념(얕은/깊은 복사, 이동, RAII)은 스마트 포인터의 "왜"를 설명하는 근거야.

"unique_ptr이 뭐예요?" → "raw pointer의 RAII 래퍼입니다. 스코프 벗어나면 자동 delete."
"왜 move로 unique_ptr를 넘기나요?" → "unique_ptr은 복사 불가(소유자 1명). 소유권 이전은 이동으로만."

이렇게 연결해서 답하면 기본기 있는 사람으로 보임.

전체 흐름:

① Heap에 new로 메모리 할당됨 (자료구조 시간에 배움)
② 여러 곳에서 쓸 수 있어서 포인터로 관리 (포인터 시간에 배움)
③ 복사하면 얕은/깊은 복사 문제 (이번에 배움)
④ 원본 필요 없으면 이동으로 빠르게 넘김 (이번에 배움)

"게임은 왜 UDP를 쓰나요?"
TCP의 문제:
패킷 하나가 유실되면? → TCP가 "잠깐! 재전송 기다려!" → 뒤의 모든 패킷이 멈춤
이걸 Head-of-Line Blocking이라 해.

FPS 게임에서 적의 위치 패킷이 1개 유실됐어:
• TCP: 0.1초 전 위치를 기다리느라 → 현재 위치 정보도 멈춤 → 화면 프리즈
• UDP: 유실된 건 무시하고 → 최신 위치만 바로 적용 → 살짝 텔레포트하지만 멈추진 않음

게임에서는 "0.1초 전 정보"보다 "지금 최신 정보"가 훨씬 중요해.
그래서 UDP로 최신 정보를 계속 쏘고, 중간에 몇 개 빠져도 신경 안 쓰는 게 나음.
카트라이더: 상대방 차 위치를 초당 30번 받음.
1번 빠져도? → 다음 0.033초 후에 새 위치 오니까 괜찮음.
근데 TCP였으면? → 빠진 1번 기다리느라 나머지 29번도 멈춤 = 렉

그래도 TCP 쓰는 경우:
• 채팅 (한 글자도 빠지면 안 됨)
• 로그인/인증 (보안 중요)
• 아이템 거래 (돈 관련은 절대 유실 안 됨)
• 메이플 같은 턴 기반에 가까운 게임은 TCP로도 가능
면접 답변 템플릿:
"실시간 게임은 UDP를 씁니다. TCP는 패킷 유실 시 Head-of-Line Blocking으로 전체가 멈추지만, UDP는 유실을 무시하고 최신 데이터만 처리할 수 있어서 끊김 없는 플레이가 가능합니다. 다만 중요한 데이터(로그인, 결제)는 TCP나 자체 신뢰 계층을 UDP 위에 구현합니다."
📦 3. 패킷 & 직렬화 — "데이터를 어떻게 보내나"
컴퓨터끼리 대화하려면 데이터를 "바이트 덩어리"로 변환해야 함
패킷
패킷 = "보내는 데이터 택배 상자"
네트워크로 보내는 데이터 한 덩어리 = 패킷

택배처럼 겉에 정보가 붙어있어:

헤더: "보내는 사람 IP", "받는 사람 IP", "패킷 번호", "데이터 크기"
페이로드: 실제 게임 데이터 (플레이어 위치, 공격 명령 등)
패킷 구조
헤더: 보낸 곳 192.168.1.5 → 받는 곳 10.0.0.1 | 크기: 64B | 번호: #4521
페이로드: { type: MOVE, x: 150.3, y: 0, z: 420.7, timestamp: 16847234 }
↓
직렬화
직렬화 = "C++ 객체 → 바이트 배열 변환"
네트워크로 C++ 객체를 그대로 보낼 수 없어. (포인터? 가상함수 테이블? 의미 없음)
"값만 쭉 나열해서 바이트로 변환" 해야 해. 이게 직렬화(Serialization).

보내는 쪽: 객체 → 바이트 배열 (직렬화)
받는 쪽: 바이트 배열 → 객체 복원 (역직렬화)
포톤에서 PhotonView.RPC("Attack", ...) 했을 때,
내부적으로 "Attack"이라는 문자열 + 매개변수를 바이트로 변환해서 네트워크로 보낸 거야.
상대쪽에서 받으면 다시 복원해서 Attack 함수 호출.

실무에서 쓰는 직렬화 포맷:
• Protobuf (구글): 작고 빠름. 서버-클라 통신에 많이 씀.
• FlatBuffers: 역직렬화 없이 바로 읽기 가능. 더 빠름.
• JSON: 사람이 읽기 쉬움. 근데 느리고 큼. 실시간엔 안 씀.
⏱️ 4. 레이턴시 & 동기화 — "렉은 왜 생기고 어떻게 숨기나"
서버까지 50ms 걸리면, 그 50ms 동안 뭘 보여주지?
문제
레이턴시(Ping) = "내 입력이 서버에 도달하는 시간"
서울 → 넥슨 서버: 약 10~30ms
서울 → 미국 서버: 약 150~200ms

문제: 내가 "공격!" 눌렀는데, 서버에 도달하는 데 50ms,
서버가 응답 보내는 데 50ms = 총 100ms(왕복 = RTT).

0.1초 동안 아무 반응 없으면? → "렉이다!" 느낌.
그래서 0.1초를 "숨기는" 기법들이 필요해.
↓
해결
클라이언트 예측 (Client-Side Prediction)
"서버 응답 기다리지 말고, 일단 내가 결과를 예측해서 먼저 보여줌"

① 내가 "앞으로 이동" 입력 → 서버에 보냄
② 서버 응답 기다리지 않고, 내 화면에서는 즉시 캐릭터를 앞으로 움직임 (예측)
③ 50ms 후 서버에서 "맞아, 거기로 이동 OK" 확인 옴 → 그대로 유지
④ 만약 서버가 "아니, 벽이 있어서 이동 불가" 하면? → 되돌림 (Rollback)
엘든링 협동:
내 화면에서 공격 모션은 즉시 나옴 (예측). 실제 데미지 판정은 서버(호스트)가 함.
"내가 때렸는데 안 맞았어?" → 서버에선 이미 적이 회피했던 것. 예측 실패.

카트라이더:
핸들 꺾는 즉시 내 화면에서 차가 돌아감 (예측). 서버 확인 안 기다림.
상대방 차는? 서버에서 온 위치를 보간(Interpolation)해서 부드럽게 보여줌.
↓
보간
보간 (Interpolation) — "상대방이 뚝뚝 끊기지 않게"
상대방 위치를 초당 20번 받는다고 쳐. 근데 내 화면은 60fps.
데이터 없는 40프레임 동안은? → 이전 위치와 다음 위치 사이를 부드럽게 채워넣음.

Interpolation (보간): 받은 두 위치 사이를 부드럽게 이동
→ 항상 약간 "과거"를 보여줌. 안전하지만 미세한 딜레이.

Extrapolation (외삽): "지금까지 이 방향으로 갔으니 계속 갈 거야" 예측
→ 최신에 가깝지만, 예측 틀리면 순간이동(워프) 발생.
상대방 캐릭터를 내 화면에 표시하는 방법
Interpolation

👑 5. 서버 권위 (Server Authority) — "서버가 진실"
핵을 막는 가장 기본적인 원리
원리
"클라이언트는 거짓말할 수 있다. 서버만 진실."
황금 규칙:

클라이언트가 보내는 것: "내가 뭘 하고 싶다" (입력/요청)
서버가 결정하는 것: "그게 가능한지 확인하고, 실제 결과를 계산" (판정)

❌ 클라이언트: "나 데미지 99999 줬어!" → 서버가 받아들이면 핵
✅ 클라이언트: "나 공격 버튼 눌렀어!" → 서버가 "무기 공격력 50, 방어력 적용 → 데미지 35" 계산
메이플스토리:
옛날엔 클라이언트가 데미지를 계산해서 보냈음 → 핵 천국 (데미지 핵, 스피드 핵)
현재는 서버가 데미지를 계산 → 클라이언트가 뭘 보내든 서버가 무시할 수 있음 → 핵 방지

발로란트:
히트 판정을 100% 서버에서 함. "내 화면에선 맞았는데?" 해도 서버에서 안 맞았으면 미스.
이래서 "128틱 서버"(초당 128번 판정)를 자랑하는 것.
서버 권위의 정도:

• 강한 서버 권위: 모든 판정을 서버가 함. (발로란트, 메이플) → 핵 방지 강함, 렉 느껴질 수 있음
• 약한 서버 권위: 일부 판정을 클라이언트에 맡김. (엘든링 PvP) → 부드럽지만 핵에 취약

넥슨 게임은 대부분 강한 서버 권위. 서버에서 모든 전투 계산.
📋 6. 면접 정리
질문
예상 질문 + 핵심 답변
질문답변
"TCP vs UDP 차이?"TCP: 도착 보장, 순서 보장, 느림. UDP: 보장 없지만 빠름. 게임은 최신 데이터가 중요해서 UDP 기반, 중요 데이터만 자체 신뢰 계층 추가.
"게임에서 UDP 쓰는 이유?"TCP는 패킷 유실 시 Head-of-Line Blocking으로 전체 멈춤. UDP는 유실 무시하고 최신만 처리 → 끊김 없음.
"클라이언트 예측이 뭐예요?"서버 응답 전에 입력 결과를 로컬에서 먼저 보여줌. 서버 확인 후 틀리면 Rollback.
"서버 권위란?"게임의 진짜 상태는 서버만 결정. 클라이언트는 입력만 보내고, 판정/계산은 서버가 함. 핵 방지의 핵심.
"보간 vs 외삽?"보간: 받은 두 위치 사이를 부드럽게. 약간 과거. 외삽: 마지막 방향으로 예측. 최신이지만 워프 가능.
"직렬화가 뭐예요?"C++ 객체를 바이트 배열로 변환해서 네트워크 전송 가능하게 만드는 것. 받는 쪽에서 역직렬화로 복원.
넥슨 면접이면 이 질문은 거의 확정:
"TCP와 UDP의 차이를 설명하고, 게임에서 어떻게 활용하는지"

여기에 "Head-of-Line Blocking" 용어 + "자체 신뢰 계층" 언급하면 가산점.
