📌 우선순위 큐 (Priority Queue)

보스가 독, 화상, 출혈 3개 디버프를 걸었어. 3초 후 독 데미지, 5초 후 화상, 8초 후 출혈.
가장 급한 것(3초 독)부터 꺼내야 해. 이게 우선순위 큐야.
"시간순으로 줄 세워놓고, 제일 빠른 거 먼저 처리"
연산비용설명
삽입 (push)O(log n)새 이벤트를 넣으면 자동으로 정렬 위치 찾아감
꼭대기 확인 (top)O(1)가장 급한 게 뭔지 바로 확인
꺼내기 (pop)O(log n)꼭대기를 빼고 재정렬

왜 배열 정렬이 아니라 우선순위 큐?

방식삽입최솟값 꺼내기게임에서
정렬된 배열O(n) (끼워넣기)O(1)삽입이 느림
정렬 안 된 배열O(1)O(n) (전부 뒤짐)꺼내기가 느림
우선순위 큐 (힙)O(log n)O(log n)둘 다 빠름!
우선순위 큐 = "가장 급한 것부터 꺼내는 자료구조"
내부는 Heap(힙)으로 구현. 삽입/꺼내기 둘 다 O(log n).

📌 힙 (Heap) — 우선순위 큐의 내부 구조

힙이 뭐냐

"부모가 자식보다 항상 작은(또는 큰) 이진 트리"를 배열로 구현한 것.

3 ← 꼭대기 (가장 작은 값 = 가장 급한 이벤트) / \ 5 8 / \ / \ 10 15 12 20 배열로 저장하면: [3, 5, 8, 10, 15, 12, 20] 0 1 2 3 4 5 6 부모 인덱스 = (자식 - 1) / 2 왼쪽 자식 = 부모 × 2 + 1 오른쪽 자식 = 부모 × 2 + 2
엘든링 이벤트 스케줄러:
• 3초 후: 독 데미지 → 힙 꼭대기
• 5초 후: 화상 데미지
• 8초 후: 출혈 데미지
매 프레임 꼭대기만 확인 → "3초 됐나?" → 아직이면 아무것도 안 함 → O(1)
3초 지남 → pop → 독 처리 → 다음 꼭대기는 5초 화상

⚠️ "메모리 힙"과 다른 것!

자료구조 힙 (Heap)메모리 힙 (Heap)
정체트리를 배열로 구현한 자료구조동적 메모리 할당 영역
관계우선순위 큐의 내부new로 할당하는 RAM 영역
이름만 같음✅ 완전히 다른 개념!

게임에서 우선순위 큐 쓰는 곳

용도왜 우선순위 큐?
A* 길찾기가장 유망한(비용 낮은) 노드부터 탐색
이벤트 스케줄러3초 후 독, 5초 후 화상 → 시간순 처리
AI 행동 우선순위위협도 높은 적부터 처리
네트워크 패킷중요도 높은 패킷 먼저 전송
"우선순위 큐는 가장 급한 것부터 꺼내는 자료구조입니다. 내부는 힙(Heap)으로 구현되며, 삽입과 꺼내기 모두 O(log n)입니다. 게임에서는 A* 길찾기에서 가장 유망한 노드를 꺼내거나, 이벤트 스케줄러에서 시간순으로 디버프를 처리할 때 사용합니다. 메모리 Heap과는 이름만 같고 전혀 다른 개념입니다."

📌 벡터 연산 — 4단계

STEP 1. 방향 벡터 (어디에 있냐)

적 위치 - 내 위치 = 방향 벡터

(8, 6) - (2, 3) = (6, 3)  → "적이 오른쪽 위에 있다"

STEP 2. Magnitude / 길이 (얼마나 멀리)

길이 = √(x² + y²) = √(36 + 9) = √45 ≈ 6.7

STEP 3. 정규화 / Normalize (순수 방향만)

각 성분 ÷ 길이 = (6/6.7, 3/6.7) ≈ (0.89, 0.45)

→ 길이가 1인 순수 방향 벡터

STEP 4. 내적 / Dot Product (앞이냐 뒤냐)

내적 = Forward · 적방향
     = Fx×Dx + Fy×Dy + Fz×Dz
     = 숫자 하나!

양수 → 앞 | 0 → 옆 | 음수 → 뒤

🎮 락온 vs 뒤잡 — 기준만 바뀜

판정Forward 기준방향 벡터조건
락온 (적이 내 앞?)나의 Forward적 위치 - 내 위치내적 > 0
뒤잡 (내가 적 뒤?)적의 Forward내 위치 - 적 위치내적 < 0
공식은 똑같아. Forward를 누구 걸로 쓰냐만 다름!
"적까지 방향 벡터를 구해서 정규화하고, 플레이어의 Forward 벡터와 내적합니다. 양수면 앞, 음수면 뒤입니다. 시야각 판정, 락온, 백스탭 등에 활용합니다."

📌 AoS vs SoA — 캐시 효율의 핵심

AoS (Array of Structs) — 구조체 배열

메모리: [x,y,z,hp,atk,alive] [x,y,z,hp,atk,alive] [x,y,z,hp,atk,alive] ←── Enemy 1 (100B) ──→ ←── Enemy 2 (100B) ──→ 캐시 라인 (64바이트) 읽으면: [x, y, z, hp, atk, alive, ...] ← hp 4바이트만 필요한데 60바이트 낭비!

SoA (Struct of Arrays) — 배열의 구조체

메모리: [hp][hp][hp][hp][hp][hp][hp][hp][hp][hp][hp][hp][hp][hp][hp][hp] ←── 캐시 라인 하나에 HP 16개! 낭비 0! ──→
AoS (구조체 배열)SoA (배열의 구조체)
캐시 라인 1회HP 1개 + 쓸데없는 데이터HP 16개
HP만 순회 시캐시 미스 많음캐시 히트 연속
한 객체 전체 접근빠름 (다 모여있으니까)느림 (흩어져 있으니까)
게임 사용일반적인 OOPECS (Entity Component System)
"하나의 필드만 순회할 때는 SoA가 압도적으로 빠르다" = 캐시 라인을 100% 활용
ECS가 빠른 이유 중 하나가 이 SoA 구조.
"구조체 배열(AoS)은 HP를 읽을 때 불필요한 데이터까지 캐시에 올라와서 캐시 낭비가 발생합니다. HP만 따로 배열(SoA)로 두면 캐시 라인 하나에 HP 16개가 들어가서 공간적 지역성이 극대화됩니다."

📌 상태 패턴 (State Pattern) — if-else 지옥 탈출

❌ Before: if-else 체인

void Update() {
    if (state == "Idle") { /* ... */ }
    else if (state == "Run") { /* ... */ }
    else if (state == "Attack") { /* ... */ }
    // 상태 추가할 때마다 여기 수정... 💥
}

✅ After: 상태 패턴

class IState {
    virtual void Enter() = 0;
    virtual void Update() = 0;
    virtual void Exit() = 0;
};

class IdleState : public IState { /* ... */ };
class RunState : public IState { /* ... */ };

// Player는 현재 상태만 들고 있음
class Player {
    IState* currentState;
    void Update() {
        currentState->Update();  // if문 없음!
    }
};
if-else상태 패턴
상태 추가Update() 수정클래스 하나만 추가
Update() 크기수백 줄한 줄
디버깅전체를 봐야 함해당 상태 클래스만
상태 패턴도 상태 15개+ 되면 클래스 폭발 가능. 동시 상태(걸으면서 공격)는 레이어드 FSM 또는 컴포넌트 분리로 해결.

📌 터널링 (Tunneling) — 벽 뚫기 버그

프레임 1: 캐릭터 [■] |벽| ←── 속도 빠름 ──→ 프레임 2: |벽| [■] ← 벽을 뚫고 지나감! → 프레임 사이에 충돌 검사가 없어서 벽을 "터널처럼" 통과

해결 방법

방법설명언리얼에서
CCD프레임 사이 궤적을 연속 검사Sweep
레이캐스트이동 전에 앞에 벽 있는지 검사LineTrace
속도 제한1프레임 이동 < 콜라이더 두께Max Speed 설정
벽 두껍게응급 처치콜라이더 크기 조절
"터널링 현상을 의심합니다. 속도가 빨라서 한 프레임에 콜라이더를 넘어가버리는 겁니다. CCD(Continuous Collision Detection)로 프레임 사이 궤적을 연속 검사하거나, 레이캐스트로 앞에 벽이 있는지 먼저 확인합니다."
